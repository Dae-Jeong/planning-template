# __PROJECT_NAME__ Policy QA Checklist

최종 수정: __DATE__

SPEC 초안 발행 전, 정책/UX 계약 변경 시, 그리고 Release Gate 직전에 누락을 잡는 점검표입니다.

## 적용 시점

- 새 SPEC 초안 작성 후
- 인증 · 권한 · 데이터 상태 머신 · 비용/할당량 정책 변경 시
- Release Gate 전 QA 시나리오 도출 시

## 1. 7대 케이스 범주

| 범주 | 핵심 질문 |
| --- | --- |
| **Happy Path** | 필수 조건이 갖춰졌을 때 핵심 가치가 막힘없이 전달되는가 |
| **Failure** | 외부 연동 장애, 검증 실패, 네트워크 단절 시 사용자가 원인과 다음 행동을 아는가 |
| **Boundary** | 길이·금액·횟수·시간·재고 등의 경계가 하드코딩이 아니라 정책 변수와 경계값으로 정의됐는가 |
| **Empty State** | 초기 데이터 없음, 검색 결과 0건 상태가 고장 난 화면처럼 보이지 않는가 |
| **Permission** | 미로그인, 권한 부족, 비활성/탈퇴 후 접근 시 데이터 누설 없이 차단되는가 |
| **State Exposure** | 목록 · 상세 · 알림 · API 등 다른 화면이 같은 상태를 모순된 용어로 말하지 않는가 |
| **E2E Flow** | 진입 → 실행 → 새로고침/재진입 → 후속 확인까지 흐름이 끊기지 않는가 |

## 2. 내적 정합성 점검 (자기 모순 방지)

- `10-decision.md`에서 Out of Scope로 제외한 기능이 SPEC 흐름/CTA에 슬쩍 섞여 있지 않은가?
- "권한 없으면 불가"라고 해놓고 직접 URL 진입이나 백엔드 조회 경로를 열어두지 않았는가?
- "비동기 처리"라고 해놓고 화면에서는 즉시 완료처럼 간주하는 계약이 섞이지 않았는가?
- 사용자 화면(`UX Contract`)에 내부 컬럼명·에러코드·벤더 명칭이 그대로 노출되지 않는가?

## 3. QA 검증형 서술 규칙

SPEC 본문은 `OOO가 안 된다`, `보이면 안 된다`, `미구현`처럼 반쪽짜리 부정 서술로 끝내지 않습니다:

- **권장 골격**: `조건(When) → 기대 화면/상태/문구/CTA → 사용자 결과 → QA 판정 기준`

## 4. 테스트 가능성 라벨

모든 AC / QA 시나리오는 아래 5개 라벨 중 하나로 분류해 수동-only 항목을 명시합니다:

- `qa-alone`: 화면 조작만으로 QA 단독 검증 가능
- `dev-setup`: 시드 데이터, 다중 계정, mock 환경 준비 필요
- `external-schedule`: 외부 provider, OS 백그라운드, 배치 시간 경과 등 별도 일정 필요
- `alternative-needed`: 실장애 직접 재현이 어려워 replay / forced state / log 근거로 대체
- `design-review`: 레이아웃, 대비, 문구 톤 등 시각 중심 검수 필요
